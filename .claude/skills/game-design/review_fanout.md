# 리뷰 모드 — 팬아웃 전수 점검

> `game-design` 의 리뷰 모드에서 쓴다. "기획 전체 리뷰" · "모순 찾기" · "전수 점검" 요청일 때.
>
> 목차 — 1 원칙 · 2 문서 묶음 · 3 에이전트 프롬프트 템플릿 · 4 종합 4단계 · 5 최종 판정 템플릿

## 1. 원칙

- **동시에 띄운다** — 묶음별 서브에이전트를 **한 메시지 안에서 전부** 호출한다. 순차 실행 금지
- **`model: "sonnet"`** — 조사·독해 작업이다. 메인 컨텍스트로 직접 grep 하지 않는다
- **에이전트는 읽기만 한다** — 문서를 고치지 않고, 파일을 만들지 않는다. 산출은 메시지 본문뿐
- **출력 3분류 고정** — 아래 템플릿의 A / B / C 밖으로 나가지 않는다
- **판정은 메인이 한다** — 에이전트는 재료를 모으고, 충돌 판정 · 컨셉 락 대조 · 최종 판정은 메인의 몫
- **수정은 사용자가 요청할 때만** — 리뷰는 판정까지다

## 2. 문서 묶음

`docs/game_design/` 을 도메인으로 자른 것. 문서가 늘면 묶음을 다시 나눈다.

| 묶음 | 담당 문서 |
|---|---|
| 전투 · 몬스터 | `battle_design.md` · `monster_design.md` |
| 영웅 · 스킬 | `hero_design.md` · `skill_design.md` |
| 아이템 · 전술카드 · 자원 | `item_design.md` · `tactic_card_design.md` |
| 거점 · 파견 · 스토리 | `base_expedition_design.md` · `story_chapter_design.md` |
| 화면 ↔ 기획 접점 | `docs/client/SCREEN_DESIGN.md` · `docs/client/DEV_PLAN.md` §3-2 · GAME_DESIGN §3 |

**모든 묶음이 공통으로 읽는 것** — `CLAUDE.md` 컨셉 락 · `docs/game_design/GAME_DESIGN.md` §1 · §2 · §9 · §10.

## 3. 에이전트 프롬프트 템플릿

`<…>` 만 채워서 그대로 쓴다.

```
당신은 TheSevenSimulationRPG 기획 전수 점검의 「<묶음 이름>」 담당입니다.

## 읽을 것 (전문)
- <담당 문서 목록 — 프로젝트 루트 기준 경로>
- CLAUDE.md 의 「컨셉 락」 절 (따름정리 셋)
- docs/game_design/GAME_DESIGN.md §1(게임 정의) · §2(설계 검증 기준) · §9(결정 로그) · §10(미확정 과제)

## 하지 말 것
- 문서를 수정하지 않는다. 파일을 만들지 않는다. 커밋하지 않는다
- 담당 밖 문서를 전문으로 읽지 않는다 — 궁금하면 C 분류에 질문으로 남긴다
- 수치를 새로 제안하지 않는다. 값은 CSV 가 정한다

## 판정 순서
모순 → 빈 구멍 → 이중 처벌 → SSOT 위반 → 그 다음에야 재미.
"이미 §10 에 올라 있는가"를 먼저 확인한다 — 올라 있으면 새 발견이 아니라 「기존 과제」로 표시한다.

## 출력 — 이 셋으로만 답한다

### A. 도메인 내 문제점
| # | 문제 | 근거(문서 §) | 분류(모순/빈 구멍/이중 처벌/SSOT) | §10 에 있나 |

### B. 다른 시스템에 대한 가정
내 담당 문서가 "다른 도메인이 이럴 것"이라고 전제하고 있는 것.
| # | 가정 | 어느 도메인에 거는가 | 근거(문서 §) |

### C. 다른 시스템에 던지는 질문
답이 없으면 내 도메인을 못 닫는 것.
| # | 질문 | 받을 도메인 | 못 닫히는 것 |

각 표는 근거 절 번호를 반드시 채운다. 확인 못 한 것은 쓰지 않는다.
```

## 4. 종합 4단계 (메인)

1. **가정 충돌 대조** — 모든 묶음의 B 를 모아, 같은 대상에 대한 가정이 서로 어긋나는 쌍을 찾는다. 어긋난 쌍은 **모순**이다 (양쪽 다 "확정"이라 믿고 있으므로 §10 에도 없다)
2. **질문 배분 · 응답** — C 를 받을 도메인별로 나눠, 그 도메인의 A/B 와 해당 문서에서 답이 나오는지 본다. 답이 없으면 **빈 구멍** 후보
3. **수치 박힘 grep** — `docs/game_design/` 전체에 돌리고 한 줄씩 판정한다 (허용 목록은 셀프 리뷰 체크리스트에)
   ```bash
   grep -rnE "[0-9]+%|[0-9]+초|[0-9]+분|HP [0-9]+|\+[0-9]+" docs/game_design/
   ```
4. **컨셉 락 · 검증 기준 대조** — 1~3 에서 나온 항목을 CLAUDE.md 따름정리 셋과 GAME_DESIGN §2 다섯 기준에 하나씩 댄다

## 5. 최종 판정 템플릿

```
## 기획 전수 점검 — YYYY-MM-DD
점검 범위: <묶음 이름 나열> · 근거는 전부 문서 § 로 표시

### 1. 컨셉 락 위반
| # | 항목 | 부딪히는 조항 | 근거(문서 §) | 판정 |
(없으면 "없음" 한 줄)

### 2. 시스템 간 모순 — 가정 충돌
| # | 한쪽 주장 | 다른 쪽 주장 | 근거(양쪽 §) | 어느 쪽이 옳은가 / 미정 |

### 3. 빈 구멍 — §10 에도 없는 것
| # | 무엇이 안 닫혔나 | 어느 도메인이 막히나 | 근거(§) |

### 4. SSOT 위반
| # | 위치 | 무엇 (수치 박힘 / 폐기 어휘 / 교차 링크 단절) | 조치안 |

### 5. §10 갱신 제안
| # | 과제 | 들어갈 분류(큰 틀/시스템/수치·밸런스) | 제안 문장 |

### 6. 판정
- 지금 당장 닫아야 하는 것: <목록 — 다른 결정을 막고 있는 순서로>
- §10 에 올리고 미루는 것: <목록>
- 이번 점검에서 확인만 하고 넘어간 것: <목록>
```

- 판정은 **막고 있는 순서**로 정렬한다 — 이것이 안 정해져서 다른 게 못 가는 것이 위
- 수정은 하지 않는다. 사용자가 "반영해"라고 할 때 절차 3 으로 넘어간다
