## 결정

게임 화면에서 **Ctrl + 휠**(Windows 터치패드 핀치도 Chrome 에선 Ctrl + 휠로 온다)과 **Ctrl + `+` · `-` · `=`**(Mac 은 ⌘)을 `preventDefault` 로 삼킨다 — 브라우저 확대/축소가 일어나지 않는다. **Ctrl + 0 은 막지 않는다.** 리스너는 `app.js:boot` 에서 `fitStage` 를 거는 자리 옆에 건다 · 휠은 `{ passive: false }` 로 건다.

## 맥락

- 2026-09-24 사용자 보고 「테두리 선들이 갑자기 굵어졌다」. 코드에는 테두리를 통째로 바꾼 변경이 없었고, 사용자의 Chrome 에 **localhost 확대/축소 25%**(`zoom_level -7.60` · 12:08 저장)가 들어 있었다
- 한 장은 `fitStage` 가 `transform: scale(s)` 로 창에 맞춘다 — 배율 상한이 없어 25% 면 CSS 창이 4배로 넓어지고 **s 도 4배**가 된다. 글씨 · 그림 · 칸은 그만큼 도로 커져 **화면이 평소와 똑같이 보인다** — 사용자는 축소된 줄 모른다
- 테두리만 다르다 — Chrome 은 테두리 폭을 **transform 전에 기기 픽셀로 반올림**한다(1 기기 픽셀 미만은 1 로). 25% 에서 1px 선은 0.25 → 1 기기 픽셀이 되고, 그것이 scale(4) 로 **4px** 이 된다. 1 · 2 · 3px 선이 전부 같은 굵기로 선다(Chrome 126 헤드리스 실측 — 기기 배율 0.25 · 창 6400×3200 에서 1px 선 3~4px)

## 근거

- **화면은 배율을 안 탄다** — 한 장이 늘 창을 채우므로 브라우저 확대/축소는 이 게임에서 **보이는 이득이 없고 테두리만 망가뜨린다**. 막아서 잃는 것이 없다
- **입력이 가장 흔한 길이다** — Ctrl + 휠은 스크롤하다 Ctrl 을 쥔 채로도 들어간다. 사용자가 모르게 25% 까지 내려간 경로가 이것일 공산이 크다
- **Ctrl + 0 은 탈출구다** — 페이지는 **이미 저장된 배율**과 **Chrome 메뉴(⋮)의 확대/축소**를 못 막는다. 그렇게 바뀐 배율을 되돌리는 손이 Ctrl + 0 이다. 이것까지 막으면 메뉴로 들어간 배율은 메뉴로만 풀린다

**버린 안**

1. **`fitStage` 를 CSS `zoom` 으로** — 한 장의 배율을 `zoom` 으로 걸면 테두리 반올림이 배율 뒤에 일어나 **어떤 브라우저 배율에서도 똑같이 보인다**(메뉴 · 저장된 배율까지 무력화). 버린 이유 — ① `tip.js:stagePoint` · `stageRect` 가 `#stage` 의 transform 행렬을 뒤집는 구조라 좌표 계산을 다시 짜야 한다(툴팁 · 드래그 고스트) ② 터치 기기의 눕힘(ADR-0109)은 회전이라 `zoom` 만으로 안 되어 둘을 섞어야 한다 ③ 같은 날 넣은 Chrome 127 이하의 `zoom` 사각형 보정(`rectZoom`)과 얽히고, 헤드리스 검증 브라우저(Chrome 126)가 옛 방식이다 ④ 창이 한 장보다 클 때(s > 1) 테두리가 지금보다 얇게 선다 — 평소 화면의 인상이 바뀐다
2. **배율을 재서 경고 띄우기** — 페이지는 브라우저 배율을 직접 못 읽는다(`devicePixelRatio` 는 OS 배율과 섞인다 · `outerWidth / innerWidth` 는 전체화면 · 개발자 도구에서 틀린다). 경고 문턱을 정할 값이 없다
3. **Ctrl + 0 까지 막기** — 위 근거 셋째 줄
