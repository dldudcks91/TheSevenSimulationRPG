# 코드 구현체계 검증 결과

검증일: 2026-09-18. 대상: 커밋되지 않은 변경을 포함한 현재 작업 트리.

**판정: 계층 분리와 결정론의 기본 골격은 작동한다. 그러나 ‘모순 없이 올바르다’고 판정할 수는 없다. 전투·화면·저장 경계에서 재현되는 결함 10건과 데이터·문서 관리 문제 2건을 확인했다.**

게임 소스와 CSV, 골든 스냅샷은 수정하지 않았다. 이 폴더에 검증 스크립트와 증거만 추가했다. 아래 발견 사항은 수정 완료 목록이 아니라 수정해야 할 목록이다.

## 1. 검증 기준과 작업 중 변경

- 게임 규칙: `GAME_DESIGN.md`, 전투·영웅·아이템·스킬·원정·몬스터·전술 기획서의 관련 규칙.
- 구현 계약: `ARCHITECTURE.md`, `INTERFACE.md`, 각 소스 폴더 README.
- 알려진 부채와 미구현: `DEV_PLAN.md`, 기획서 미확정 항목.
- 수치: 실제 CSV. 문서의 표 개수·과거 측정값은 그대로 신뢰하지 않고 재집계했다.
- 검증 방식: 핵심 실행 경로 정적 검토, 기존 브라우저 테스트, 독립 기대값, 상태 불변조건, 시드 재실행, 브라우저 화면·저장 실패 주입.

첫 기존 테스트 실행은 **PASS 347/347**이었다. 검증 중 다른 작업에서 `class.csv`, `src/dev/test.js` 및 기획 문서들이 변경됐다. 최신 직업 데이터는 기사 주력 축 `str`, 궁수 `agi`, 암살자 `luck`이다. 관련 문서를 다시 읽고, 기존 테스트·확장 검증·집중 검증·화면 검증을 변경 후 상태에서 확인했다.

마지막 기존 테스트는 **344/347 통과**다. 실패 3개는 모두 골든 비교이며 다음과 연결된다.

1. `class.csv` 원문 해시: `cb3de6c1 → d53d6696`.
2. 시작 영웅 11명의 생성 결과가 기존 스냅샷과 다름.
3. 전투 50개 중 35개가 기존 스냅샷과 다름.

입력 변경과 연결된 불일치이므로 이것만으로 의도하지 않은 회귀라고 확정하지 않았다. **새 결과가 정답인지 검토하기 전에 골든을 다시 찍어 통과시키지 않았다.** 초기 통과는 최초 도구 실행 결과이며, `baseline.json`과 `baseline.html`은 마지막 실행 결과다.

각 실행의 `*_manifest.json`은 소스·CSV·문서 SHA-256을 기록한다. `*_changes_during_run.json`은 실행 도중 변화를 기록한다. 캠페인 실행 중 `src/dev/test.js`가 바뀌었지만 해당 실행은 `sim.html`/`sim.js`를 사용한다. 마지막 나머지 실행의 도중 변경 목록은 비어 있다. 서로 다른 시점의 결과를 하나의 불변 스냅샷으로 주장하지 않는다.

## 3. 재현된 결함

우선순위 P1은 데이터 손실 가능성 때문에 먼저 수정할 항목, P2는 실제 규칙·상태·표시 오류, P3는 데이터·문서 관리 문제다. 숫자는 심각도를 자동 산정한 점수가 아니라 이번 수정 순서 제안이다.

### F01 · P2 · 스킬 피해 감소가 원천별 곱 규칙을 위반한다

- 위치: [skill_effects.js](../../src/game_logic/skill_effects.js), `EFFECTS.dr_pct` (200행).
- 기준: `battle_design.md` §9-3, `skill_design.md` 디파이언스, `skill.csv:kni_defiance` 설명은 원천별 곱을 명시한다.
- 실제: `u.dr = u.drBase + sum`으로 더한다. 기본 감소 0.2와 스킬 감소 0.3을 주면 0.5다. 기대값은 `1 - 0.8 × 0.7 = 0.44`다.
- 영향: 장비·마스터리·전술과 디파이언스/듀얼을 함께 쓸 때 의도보다 강하게 감소한다. 스킬끼리도 합쳐진다.
- 조치: 스킬 버프를 원천별로 곱해 기존 감소에 결합한다. 손계산 단정과 실제 디파이언스+듀얼+마스터리 조합을 함께 고정한다.

### F03 · P2 · 같은 오오라를 가진 한 명이 교체하면 다른 시전자 효과도 사라진다

- 위치: [battle.js](../../src/game_logic/battle.js), `applyAuras` 504~521행 및 `refit` 998~1007행.

### F04 · P2 · 최대 HP 버프의 계산 결과가 재생 화면에 전달되지 않는다

- 위치: [skill_runtime.js](../../src/game_logic/skill_runtime.js) `castBuff` 140~148행; [skill_effects.js](../../src/game_logic/skill_effects.js) `hp_max_pct`; [ui/battle.js](../../src/ui/battle.js) `buff`/`buffEnd` 처리.

- 원인: `buff`는 효과량과 `amt`만 보내며 재생기는 버프 뱃지만 변경한다. 새 현재 HP·최대 HP를 받지 않는다. `amt`가 있다는 이유로 로그도 방벽 문구를 고른다.

### F07 · P2 · ‘불러오기 가능’ 판정이 손상된 참조·필수 데이터를 통과시킨다

- 위치: [state.js](../../src/game_logic/state.js), `canLoad`/`deserialize` 702~757행.
- 재현: 정상 세이브에서 각각 ① 존재하지 않는 영웅을 party에 추가 ② 착용 아이템을 bag에도 추가 ③ 영웅 레벨을 상한+1로 변경 ④ resources 삭제. 네 경우 모두 `canLoad === true`다.
- 원인: 버전 변환과 기본값 보완은 있지만 최종 스키마·참조·소유권 검증이 없다.
- 영향: 시작/클라우드 선택 화면이 사용 가능한 저장으로 제시한 뒤 출발·계산·렌더에서 예외나 중복 소유 상태가 발생할 수 있다.
- 조치: 이관 후 필수 필드, 유한 수치, UID 유일성·참조, 아이템 단일 소유, 레벨·진형·카운터 범위를 검증한다. 거절 시 원본 사본을 보존한다.
- 증거: `extended.json`의 `save validation…` 네 항목. 정상 왕복 통과는 손상 검증을 대신하지 못한다.

### F08 · P1 · 로컬 저장 실패 뒤에도 클라우드 사본을 적용했다고 기록한다

- 위치: [ui/app.js](../../src/ui/app.js), `save` 77행, `adoptRemote` 647~655행; [storage.js](../../src/ui/storage.js), `writeSave`.
- 재현: 격리된 브라우저에서 게임 저장 키의 `setItem`에 `QuotaExceededError`를 주입한다. `adoptRemote(rev=42)` 호출 후 로컬 사본은 그대로인데 cloud link는 rev 42로 전진하고 상태는 on이 된다.
- 원인: `writeSave`는 실패를 false로 돌려주지만 호출부가 반환값을 무시한다.
- 영향: 동기화 완료 표기가 사실과 달라지고, 이후 push가 최신 rev를 기준으로 낡은 로컬 사본을 다시 올릴 수 있다. 일반 로컬 저장 실패도 사용자에게 드러나지 않는다.
- 조치: 쓰기 성공을 확인한 뒤에만 링크·상태·reload를 진행한다. 실패 시 현재 메모리 상태와 원본 사본을 보존하고 동기화 상태를 실패로 표시한다. 링크 저장 실패도 다룬다.
- 증거: `ui_logic.json`의 `storage failure…`. 실제 Firebase 쓰기는 수행하지 않았으며 후속 원격 덮어쓰기는 코드 경로에 근거한 위험 분석이다.

### F09 · P2 · 저장 시각만 같으면 내용이 다른 사본도 같다고 간주한다

- 영향: 같은 밀리초의 두 상태나 서로 다른 기기 사본이 충돌로 인식되지 않을 수 있다.

- 증거: `ui_logic.json`의 `cloud comparison…`. 재현을 위해 같은 시각을 명시적으로 구성했으며 실제 발생 빈도를 측정한 것은 아니다.

### F10 · P2 · 시스템 조립이 전달된 영웅 등급 데이터를 무시한다

## 6. 밸런스와 테스트 체계에 대한 해석

마지막 시작 파티 캘리브레이션은 101 승리 **2/20**, 102 **3/20**이다. 테스트 화면의 목표(각각 70% 이상, 30~70%)보다 낮다. 이전 문서에도 목표 미달이 기록돼 있으므로 새로운 구조 버그로 집계하지 않았다. 표본 20개만으로 모집단 승률을 확정하지 않는다. F05 때문에 전투불능 인원 집계는 먼저 고쳐야 한다.

3,000런 캠페인은 끝까지 실행됐고, 100런 시점 평균 클리어 스테이지 수는 18.2였다. 이 봇은 고용·수색·마스터리 투자·강화·제작을 사용하지 않으며, 장비를 공격력/방어 기준으로만 고른다. 따라서 이 숫자는 게임 전체의 재미·난이도·완주 가능성을 판정하지 않는다.

기존 테스트는 데이터·단위 공식·이관·생성 규칙을 폭넓게 다루고 있다. 문제는 테스트의 수보다 **서로 다른 경계를 함께 지나가는 사례**다. 특히 아래 불변조건이 보강돼야 한다.

- 출처가 다른 같은 스킬의 슬롯 정체성과 쿨타임이 라운드/재장착/재생에서 보존된다.
- 피해 감소의 계산은 어느 출처에서 왔든 같은 곱 규칙을 따른다.
- 버프 적용/해제 직후 재생기 상태가 시뮬의 authoritative 상태와 같다.
- `downed`는 실제 출발 영웅의 UID만 포함하며 파티 인원을 넘지 않는다.
- 상태 변경 후 진형의 UID 집합은 현재 파티와 일치한다.
- 정상 로드된 상태에는 소유권·참조·유한 수치 위반이 없다.
- 저장 실패 뒤에는 성공 표시, 클라우드 기준 rev 변경, 자동 업로드가 진행되지 않는다.
- 입력 변경으로 골든이 깨진 경우 입력·출력·의도된 규칙 변경을 검토한 다음 갱신한다.

## 7. 수정 권장 순서와 완료 기준

1. **저장 F08 → 로드 F07 → 사본 비교 F09**: 데이터 보존을 먼저 확보한다. 실패 주입/다중 탭/사본 선택을 한 묶음으로 회귀 검증한다.
2. **슬롯 계약 F02**: 인터페이스를 정한 뒤 엔진·타임라인·UI를 함께 바꾼다. 한 레이어만 바꾸면 다시 어긋난다.
3. **전투 F01/F03/F05**: 계산 규칙·오오라 공급자·전투불능 집계 수정 후 독립 기대값과 모든 스테이지 재현성을 확인한다.
4. **화면 F04, 상태 F06, 조립 F10**: 각각 버프 전후 재생, 해고 후 저장/재출발, 대체 데이터 주입으로 검증한다.
5. **CSV F11, 문서 F12**: 엄격한 입력 검증과 현행 문서를 맞춘다.
6. 위 수정과 직업 데이터 변경의 의도를 검토한 뒤 골든 갱신과 캘리브레이션을 진행한다. 밸런스 조정은 공식 오류 수정과 구분한다.

각 항목은 재현 테스트가 통과하고 관련 기존 테스트가 통과하며, 해당 계약 문서와 화면이 일치할 때 닫는다. 현 상태에서 결함 항목은 모두 열려 있다.

## 8. 검증 한계

- 전체 스테이지·몬스터·직업 스킬을 실행했지만 모든 장비·스킬·시각·입력의 조합을 전수 증명한 것은 아니다.
- 실제 Google 로그인·Firestore 보안 규칙·외부 네트워크 장애 복구는 라이브 계정으로 실행하지 않았다. 클라우드 비교/로컬 저장 실패는 격리 브라우저에서 재현했고 트랜잭션 코드는 정적으로 검토했다.
- 모바일은 Chromium 터치 에뮬레이션이다. 실제 iOS Safari 주소창·백그라운드 정책은 검증하지 않았다.
- 화면 44경로는 실행·텍스트 검사이며 모든 픽셀·툴팁·드래그 경우의 완전한 시각 검증이 아니다. 대표 4개 화면은 캡처를 직접 확인했다.
- 3,000회 시뮬레이션은 연속 계산 안정성 검사다. 며칠간 실제 브라우저를 켜둔 메모리·타이머 안정성을 보증하지 않는다.
- 세이브 이관은 기존 버전별 합성 테스트와 추가 왕복으로 검증했다. 실제 출시 이력이 있는 모든 사용자 세이브 원본을 확보한 것은 아니다.

확인 가능한 구현 범위의 검증은 수행했고, 재현된 결함·기획 공백·외부 환경 미검증을 구분해 남겼다.
