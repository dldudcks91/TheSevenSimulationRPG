# 상태 전이 감사

실제 `src`는 변경하지 않았다. `run_state.py`는 실행 시작 시 JS/CSV를 메모리에 고정하고 별도 Edge 프로필에서 독립 실행한다. `source_manifest.json`은 검증한 소스의 SHA-256이며, `results.json.changed_sources`는 검증 중 수정된 소스다. 최종 실행에서 변경 감지 0, 페이지 예외 0.

재현: 저장소 루트에서 `python output/2026-10-30_code_audit/state/run_state.py`.

## P2 — 앱의 방문객 정산이 연구 완료보다 먼저 실행되어 오프라인 수색 결과가 달라진다

- 위치: `src/ui/app.js:3294` (`visitSettle`), `src/ui/app.js:3297` (`labSettle`); 시간 분할 처리는 `src/game_logic/state.js:2921`.
- 앱은 오프라인 복귀 후 먼저 현재 시각까지 방문객을 연구 이전 값으로 생성하고, 이어서 `labSettle`이 연구 완료 시각으로 돌아가 과거/미래 구간을 다시 처리한다.
- 대기 칸 연구 0→1: 첫 방문까지 4시간, 연구 완료 1시간, 10시간 뒤 복귀. 정상 시간순 정산은 4시간/8시간에 두 명이며 다음은 12시간이다. 앱 순서는 4시간/8시간/5시간에 세 명을 만든다. 도착 순서까지 거꾸로 된다.
- 간격 연구 1→2: 연구 완료 45분, 7.8시간 뒤 복귀. 정상은 4시간/7.636시간에 두 명, 앱 순서는 4시간에 한 명이다.
- 품질 연구 0→1: seed 63, 연구 완료 20분, 24시간 뒤 복귀. 4시간째 방문객이 정상 정산에서 레어이고 앱 순서에서는 매직이다.
- `results.json`의 `visit-before-lab-waiting`, `visit-before-lab-interval`, `visit-before-lab-quality` 참조. 테스트용 속도·확률 조작 없이 현재 CSV를 사용했다.
- 제안: 연구 완료를 포함한 정산 순서를 한 곳에서 유지하고, 방문객 생성 신호도 그 결과로 앱에 돌려준다. 단순히 두 호출 순서만 바꾸면 현재 `labSettle`이 방문객을 이미 생성하므로 UI 갱신 신호를 놓칠 수 있다.
- DEV_PLAN의 현재 부채 목록에서 이 순서 오류는 확인되지 않았다.

## P2 — 동시 원정 부대가 마지막 물약 한 병을 여러 번 사용한다

- 위치: `src/game_logic/state.js:1645` (`fillSlots`), `src/game_logic/state.js:1655` (`spendPotion`), `src/game_logic/state.js:3413` (라운드 종료 후 소모 정산).
- `fillSlots`는 재고 사본만 감소시키고 그 물약을 각 런에 독립적으로 넣는다. 두 부대가 출발할 때 같은 1병을 각각 가져갈 수 있다. 라운드가 끝나고 재고를 차감할 때 이미 두 부대에서 회복 효과를 받았으며, 음수는 키 삭제로 가려진다.
- 재현: seed 1의 기본 궁수/마법사를 서로 다른 두 편성에 한 명씩 둔다. 다중 편성이 열린 세이브에서 `minor_healing=1`, 각 편성 앞 칸에 그 물약을 넣고 합법적인 HP 기준 90%로 설정한 뒤 1013에 둘 다 출발한다. 두 부대 첫 라운드를 각각 진행한다.
- 실제: 각각 3.4초에 1병을 마시고 HP 50 회복, 합계 2병 사용. 지갑 재고는 1→0→0. 기대: 가진 1병만 전체 부대에서 한 번 사용 가능해야 한다.
- `results.json.concurrent-potion-stock-overspend`에 양쪽 물약 이벤트와 재고가 기록된다. 전투 수치 변경 없이 현재 CSV로 재현했다.
- 제안: 부대 간 물약 예약/배정 또는 실제 사용 시점의 공통 재고 검증이 필요하다. 철수한 미정산 라운드는 소모를 취소한다는 기존 계약까지 함께 보존해야 한다.
- DEV_PLAN에 동시 원정 물약 재고 부채는 확인되지 않았다. 기존 물약 단정은 부대 한 개만 확인한다.
