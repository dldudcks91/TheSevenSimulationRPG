## 1. P1 — 멈춘 탭이 키보드 조작으로 활성 탭의 자동 세이브를 삭제한다

위치: `src/ui/app.js:1070`(`startGame`), `:1071`(`clearSave`), `:93`(`save`), `:928`(`renderModal`), `:1289`(`freeze`).

다른 탭이 저장하면 기존 탭에 닫을 수 없는 `frozen` 창이 뜬다. 그러나 창 뒤 버튼은 키보드 포커스를 받을 수 있다. 그 상태에서 새 게임을 실행하면 `startGame()`은 `frozen`을 검사하지 않고 `clearSave()`를 호출한다. 이어지는 `save()`는 `frozen` 때문에 저장을 생략한다. 이 두 동작이 합쳐져 현재 정상 플레이 중인 다른 탭의 자동 세이브가 사라진다.

재현:

```powershell
python output/2026-10-30_code_audit/ui/repro_frozen_keyboard_delete.py
```

1. 같은 격리 컨텍스트에서 탭 A와 B를 차례로 새 게임에 진입시킨다. B가 저장하여 A가 멈춘다.
2. A에서 Tab 20회로 창 뒤 [새 게임]에 도달해 Enter를 누른다. 창은 여전히 `frozen`이다.
3. Tab 4회로 [세이브를 지우고 시작]에 도달해 Enter, 다시 Tab 4회와 Enter로 확인한다.
4. `thesevensim.save`가 `null`이 되고 B도 저장 삭제 이벤트를 받아 멈춘다.
5. 2.1초 후에도 B는 `frozen`, 세이브는 `null`이다. B를 일반 시작 주소로 다시 열면 게임은 `null`, [불러오기]는 비활성이다.

위 단계의 게임 상태 변경은 실제 Tab/Enter와 정상 부팅 경로로만 수행했다. `G`나 `localStorage`를 테스트 코드로 직접 수정하여 삭제를 만든 것이 아니다.

증거: `repro_frozen_keyboard_delete.json`, `frozen_keyboard_deleted_a.png`, `frozen_keyboard_deleted_b.png`, `frozen_keyboard_deleted_after_reload.png`.

개선 방향: 멈춤 상태에서 게임을 바꾸거나 지우는 진입점을 거절하고, 잠긴 창이 배경 포커스·키보드 활성화를 차단하게 한다. 새 게임의 데이터 준비·저장 성공 전에 기존 세이브를 지우지 않는 순서도 필요하다. 공통 창의 포커스 문제와 멈춘 탭의 `startGame` 가드 부족을 한 결함 체인으로 센다.

## 2. P2 — 저장 한도 초과를 콘솔에만 기록하고 정상 게임처럼 계속 진행한다

위치: `src/ui/storage.js:27`(`writeSave`의 실패 반환), `src/ui/app.js:93`(반환값 무시), `:1073`(새 게임 저장 후 다음 화면으로 진행).

브라우저 저장소가 가득 차면 어댑터는 `QuotaExceededError`를 잡고 `false`를 반환한다. 호출자는 결과를 확인하지 않는다. 새 게임은 저장되지 않은 채 프롤로그에 들어가며, 화면에 저장 실패 안내가 없다. 새로고침 후에는 이어할 게임이 없다.

재현:

```powershell
python output/2026-10-30_code_audit/ui/repro_save_quota.py
```

새 격리 컨텍스트의 저장소에 테스트용 문자열을 실제 브라우저 한도까지 채운 후 정상 [새 게임]·[시작] 버튼을 눌렀다. 예외를 모킹하지 않았다. 측정된 테스트 문자열은 5,242,869자였고 실제 `QuotaExceededError`가 발생했다. 결과는 `screen='prologue'`, 게임 객체 있음, 세이브 `null`, 토스트 빈 문자열이었다. 새로고침 후 게임 `null`·불러오기 비활성이었다.

증거: `repro_save_quota.json`, `save_quota_no_warning.png`.

개선 방향: 저장 결과를 상위 호출자에 전달하고, 실패를 사용자에게 표시하며 새 게임의 저장 실패 시 정상 저장된 것처럼 다음 단계로 넘어가지 않게 한다. 기존 세이브가 있다면 성공적으로 교체하기 전까지 보존한다.

발생 범위: 저장소가 가득 찬 환경의 오류 처리 결함이다. 이번에 수집한 실제 QA 세이브 116개의 현재 형식 재직렬화 최대값은 46,103자였다. 일반 플레이만으로 저장 한도에 쉽게 닿는다는 증거는 없다. 리포트에 전투 타임라인은 저장하지 않고, 리포트·인벤토리·창고·최근 분해 기록은 각각 길이 제한이 있다.

## 3. P2 — 전투 중 갱신된 능력치가 행동 게이지·속도 제목·스킬 피해 설명에 반영되지 않는다

위치: `src/ui/battle.js:2009`(`stat`), `:2012`(`u.live`만 갱신), `:1030`·`:1041`(기존 `u.period`로 게이지 계산), `:970`(속도 제목), `:1691`(기존 공격력으로 스킬 문장 구성).

엔진의 `stat` 이벤트는 헤이스트·결빙·프렌지 등의 현재 행동 주기와 공격력 변화를 싣는다. 재생기는 이를 `u.live`에만 저장한다. 영웅 세부 옵션 툴팁은 이 값을 합쳐 읽지만, 행동 게이지와 스킬 피해 설명은 예전 `u.period`·`u.atkMin`·`u.atkMax`를 계속 사용한다.

주기 재현:

```powershell
python output/2026-10-30_code_audit/ui/repro_battle_live_display.py
```

고정 시드의 정상 전투 결과를 생성한 뒤 관전에 재생했다. 헤이스트가 적용된 전사 `p1`의 기본 주기는 2.449초, 현재 주기는 1.6327초였다. 다음 행동이 일어난 7.8초 뒤, 8.3초 시점에서 화면의 속도 제목은 2.45초, 게이지는 20.4165%로 남았다. 같은 경과 시간과 경직값을 현재 주기로 나누면 30.6241%다.

주의: 첫 자기 헤이스트 시전 시 이미 예약된 다음 행동은 유지되는 규칙이 있으므로, 이 검증은 그 다음 실제 행동 이후 구간을 사용한다.

피해 설명 재현:

```powershell
python output/2026-10-30_code_audit/ui/repro_skill_damage_display.py
```

그레이스가 적용된 전사의 물리 공격력이 8~14에서 10~17.5로 올랐다. 같은 시점의 배시 툴팁은 29~51 피해를 표시했고, 현재 공격력으로 같은 툴팁을 구성하면 36~64였다. 전투 계산은 현재 값을 사용하므로 표시와 실제 전투가 어긋난다.

증거: `repro_battle_live_display.json`, `battle_live_display.png`, `repro_skill_damage_display.json`.

개선 방향: 관전 표시가 현재 능력치를 공통으로 읽도록 맞춘다. 행동 주기는 기존 예약을 유지하는 경우까지 고려하여 표시 기준을 정하고, 실제 행동 뒤의 새 주기와 스킬 피해 설명에는 현재 값을 사용해야 한다. 두 현상은 같은 현재 능력치 동기화 누락으로 묶었다.

## 추가 확인 및 미발견 범위

- 개발 진입 경로 20개: 페이지 실행 예외 0. 결과 `smoke_ui.json`.
- 실제 QA 저장 자료 116개: v40 6개, v43 110개. 전부 `deserialize → serialize → deserialize` 성공, 정규화 반복 결과 동일. 대표 12개는 실제 메뉴의 [불러오기] 및 접근 가능한 주요 탭 클릭까지 예외 0. 결과 `saved_game_compatibility.json`.

- 주요 탭·도감 25개 화면의 툴팁 빌더 1,075회 호출: 예외·잘못된 반환 0. 실제 hover 전체 조작이 아니라 빌더 호출 검사다. 결과 `tooltip_builders.json`.
- 친선전 입력 경계 22개를 먼저 확인한 `fuzz_team_input.json`은 메인 담당에게 넘겼다. 해당 영역의 확정 판단과 중복 집계는 메인 보고서를 따른다.
- 위 검증은 모든 가능한 저장 데이터·브라우저·입력 순서의 무결성을 보장하지 않는다. 확인한 세 유형은 모두 재현 스크립트와 결과가 있다.
