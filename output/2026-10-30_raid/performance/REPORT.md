# 레이드 렉 수정 검증

## 2차 수정 — 레이드 전용 고정 표시

1차 수정 후에도 사용자가 **레이드 전투 시작 뒤에만 심한 렉이 남는다**고 알려 주었습니다. 헤드리스 테스트에서는 같은 정도의 렉을 재현하지 못했습니다. 따라서 아래 수치는 실제 사용자 환경의 해결을 입증하지 않으며, 확인한 렌더링 비용과 기능 검증 결과입니다.

- 레이드에서는 일반 관전의 스킬 그림·입자 트리·초상 brightness 필터를 더 이상 생성하지 않습니다. 10명 각각의 타격/지원 마커 2개와 숫자 3개를 재사용합니다.
- 동일 대상의 피격·회복·버프를 틱마다 묶습니다. 숫자와 상태·실제 피해·회복 집계는 모두 처리하고, 스킬·치명타 표시가 평타보다 우선합니다.
- 움직이는 속성은 opacity·scale·translate/transform으로 제한했습니다. 보스의 mask/drop-shadow와 전장의 filter, 결과창 backdrop-filter도 제거했습니다.
- 보유 영웅 최고 레벨 29/30 경계, 훈련/내 편성 공통 잠금, 직접 URL 우회 방지를 확인했습니다.

[1차 수정](after.json)과 [2차 수정](bounded_effects.json)의 같은 8초·4배속·CPU 4배 감속 조건입니다. 별도 실행이므로 환경 편차가 있으며, 새로운 세이브의 고정 훈련 편성입니다.

| 지표 | 1차 수정 | 2차 수정 |
|---|---:|---:|
| 프레임 간격 p95 | 16.8ms | 16.8ms |
| 최장 프레임 간격 | 66.6ms | 33.3ms |
| 33.4ms 초과 프레임 | 5 | 0 |
| 긴 메인 스레드 작업 | 1 | 0 |
| offsetWidth 읽기 횟수 | 15 | 0 |
| 레이아웃 계산 시간 | 470.4ms | 347.5ms |
| 메인 스레드 작업 시간 | 6,043.2ms | 4,249.7ms |

2차 수정은 메인 스레드 작업 시간이 약 30% 더 줄었습니다. [초반 이펙트 분리 측정](software_ablation.json)에서는 필터 제거만으로 큰 차이가 나지 않았으므로 필터만을 원인으로 확정하지 않습니다. [후반 측정](late_before.json)은 전투가 90.3초에 끝나 표본 후반에 대기 프레임이 포함되므로 비교 지표로 쓰지 않습니다.

최종 검증: 전체 회귀 **PASS 801/801**, 레이드 규칙 **32/32**, UI 흐름 **32/32**, 브라우저 예외·누락 아트 **0**. 전투가 진행되는 동안 전장 요소 수가 유지되고, 새 이펙트 요소 추가와 강제 폭 읽기 모두 0임을 검사했습니다. 소환물이 편성 범위를 유지하면서 실제 전투 대상 풀에 추가되는 회귀 검사도 포함합니다.

## 원인과 수정

- 게이지의 `width` 전환과 피해 숫자의 `margin-top` 이동이 프레임마다 레이아웃을 다시 만들었습니다. `scaleX`·`translate`·opacity로 바꿨습니다.
- 동일 프레임에서 보스의 피격·초상 번쩍임과 같은 공격자의 튀김을 타격마다 재시작했습니다. 대상/공격자별로 모으고 Web Animations로 재생하여 동기 배치 읽기를 줄였습니다. 실제 피해·상태·기여는 전부 처리하며 스킬 그림만 프레임 예산으로 묶습니다.
- 재시작된 일반 전투 이펙트의 완료 리스너가 이전 리스너를 남길 수 있었습니다. 노드별로 교체하여 누적을 막았습니다.
- 실제 시뮬레이션 시각이 그대로인 브라우저 프레임에도 전체 스냅샷을 만들었습니다. `run.time`이 바뀐 틱에만 스냅샷·표시를 갱신하고 동일 문구와 게이지 값은 다시 쓰지 않습니다.
- 백그라운드 원정/연구소 정산이 실행 중인 레이드 본문까지 해제·재생성할 수 있었습니다. 시계가 요청한 렌더는 셸만 갱신하며, 언어·게임·모달 전환은 전체 렌더를 유지합니다.

## 실측

로컬 Edge 헤드리스, 고정 훈련 편성, 전투 12초부터 준비 후 조건마다 벽시계 8초를 측정했습니다. 다음은 **이펙트를 켜고 4배속 재생, CPU 속도를 1/4로 제한한 조건**입니다. 새로운 세이브의 시험이므로 실제 원정 동시 실행의 비용은 포함하지 않습니다.

| 지표 | 수정 전 | 수정 후 |
|---|---:|---:|
| 프레임 간격 p95 | 33.4ms | 16.8ms |
| 최장 프레임 간격 | 116.7ms | 66.6ms |
| 33.4ms 초과 프레임 | 27 | 5 |
| 긴 메인 스레드 작업 | 6 | 1 |
| offsetWidth 읽기 횟수 | 344 | 15 |
| 동기 offsetWidth 읽기 시간 | 596.1ms | 50.8ms |
| 레이아웃 계산 시간 | 1,597.2ms | 470.4ms |
| 메인 스레드 작업 시간 | 7,847.5ms | 6,043.2ms |

이 조건에서 레이아웃 계산 시간은 약 71%, 동기 배치 읽기 시간은 약 91% 줄었습니다. 표준 CPU 조건의 4배속에서도 레이아웃 계산 시간이 457.7ms에서 150.7ms로 줄었습니다. 프레임 간격은 실제 장치·브라우저 부하에 따라 달라집니다.
